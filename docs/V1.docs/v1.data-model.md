# V1 Data Models — CodeSphere

## Status: Frozen (Aligned with V1 Architecture)

This document defines the persistent data models for V1.

It covers:

- MongoDB collections
- Domain contracts alignment
- Storage boundaries
- Indexing strategy
- Invariants
- Atomic update expectations

Canonical problem definitions are NOT stored in MongoDB.

---

# 1. Data Boundary Principles

V1 enforces strict separation:

## Canonical Content (File-Based Only)

Stored in:

#### `problem-bank/`


Never stored in MongoDB.

Includes:

- Problem description
- Constraints
- Examples
- Visible test cases
- Hidden test cases

---

## Operational State (MongoDB Only)

MongoDB stores:

- Users
- Auth identities
- Submissions
- Progress records

MongoDB does NOT store:

- Canonical problem definitions
- Hidden test cases
- Execution metadata configuration

---

# 2. Collections Overview

V1 uses the following collections:

1. users
2. auth_identities
3. submissions
4. progress

Each collection aligns with domain contracts in `packages/shared-types`.

---

# 3. Users Collection

## Purpose

Represents domain-level user identity.

## Stored Fields

- id (domain ID, string)
- email
- createdAt
- updatedAt
- disabledAt (nullable)
- deletedAt (nullable)

## Invariants

- id must be globally unique
- email must be unique
- Soft delete only (no hard delete)
- Disabled users cannot authenticate

## Indexes

- Unique index on email
- Index on id

---

# 4. Auth Identities Collection

## Purpose

Maps authentication provider identity to domain user.

## Stored Fields

- id
- userId
- provider
- providerUserId
- createdAt
- updatedAt
- disabledAt (nullable)

## Invariants

- (provider, providerUserId) must be unique
- userId must reference existing user
- Soft disable only

## Indexes

- Unique compound index on (provider, providerUserId)
- Index on userId

---

# 5. Submissions Collection

## Purpose

Stores each execution attempt result.

## Stored Fields

- id
- userId
- problemId
- language
- sourceCode
- overallStatus
- testCaseResults (array)
- totalRuntimeMs
- averageRuntimeMs
- createdAt

## testCaseResults Structure

Each entry contains:

- testCaseId
- status
- runtimeMs

No hidden test input or expected output stored.

## Invariants

- userId must exist
- problemId must exist in canonical store
- overallStatus derived from execution engine only
- createdAt immutable
- Submission records are append-only (no mutation)

## Indexes

- Index on userId
- Index on problemId
- Compound index on (userId, problemId)
- Index on createdAt (for sorting recent submissions)

---

# 6. Progress Collection

## Purpose

Tracks user-problem state.

One record per (userId, problemId) pair.

## Stored Fields

- id
- userId
- problemId
- status
  - NOT_ATTEMPTED
  - ATTEMPTED
  - SOLVED
- totalSubmissions
- lastAttemptAt
- firstSolvedAt (nullable)

## Invariants

- Unique per (userId, problemId)
- totalSubmissions ≥ 0
- Status transitions:
  - NOT_ATTEMPTED → ATTEMPTED
  - ATTEMPTED → SOLVED
  - SOLVED remains SOLVED in V1
- firstSolvedAt set only once

## Indexes

- Unique compound index on (userId, problemId)
- Index on userId

---

# 7. Atomicity Model

Submission creation and progress update must be atomic.

Allowed approaches:

- MongoDB transaction
  OR
- Idempotent logic with conditional upserts

Invalid states:

- Submission stored without progress record
- Progress updated without submission record

Atomicity is enforced at Service Layer.

Execution engine has no DB awareness.

---

# 8. Data Derivation Rules

Certain values are derived:

- overallStatus derived from testCaseResults
- progress.status derived from submission outcomes
- totalSubmissions incremented on each submission
- firstSolvedAt set when status becomes SOLVED first time

Derived fields must not be recalculated post-write.

They are immutable once persisted (except totalSubmissions).

---

# 9. Size & Storage Constraints

To prevent abuse:

- sourceCode ≤ 100KB
- testCaseResults limited by canonical test count
- No large binary storage

V1 does NOT support:

- File uploads
- Attachments
- Code artifacts
- Execution logs beyond summary

---

# 10. Soft Delete Policy

Users and auth identities:

- Soft delete only
- Preserve submission history
- Preserve progress history

Submissions and progress:

- Never deleted in V1

Data remains append-only.

---

# 11. Determinism Alignment

MongoDB stores results of deterministic evaluation.

DB must never:

- Re-evaluate submission
- Modify execution result
- Store AI-augmented evaluation

Submission results are immutable historical records.

---

# 12. Data Access Rules

Repositories must:

- Return domain-safe objects
- Never expose Mongo-specific types (ObjectId)
- Validate against shared contracts
- Not contain business logic

Service layer:

- Handles transitions
- Handles atomicity
- Handles authorization

Controllers:

- Never access DB directly

---

# 13. Future V2 Extensions

V2 may introduce:

- Execution queue records
- Container metadata
- Judge worker logs
- Execution environment metadata
- Rejudge flag
- Contest submissions

These must not break V1 contracts.

---

# 14. Data Integrity Guarantees

V1 guarantees:

- No canonical duplication
- Unique user emails
- Unique (provider, providerUserId)
- Unique progress per user-problem
- Immutable submission records
- Deterministic stored results

---

# Final Statement

V1 Data Model is:

- Cleanly separated from canonical content
- Deterministic
- Append-only where appropriate
- Transaction-aware
- Upgrade-safe
- Index-optimized
- Aligned with shared domain contracts
