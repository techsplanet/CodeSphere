# CodeSphere V1 — Execution Engine

## Status: Frozen Specification

This document defines the complete V1 execution engine architecture,
constraints, guarantees, limitations, concurrency model, and upgrade path.

This reflects exactly what V1 enforces.
No aspirational or container-level claims are made.

---

# 1. System Overview

CodeSphere V1 execution engine is:

- Server-side only
- Deterministic
- Process-based (no containers)
- Synchronous
- Single-concurrency
- File-based test driven
- Stateless
- Swappable in future versions

It exists as a separate service from the frontend and database layers.

---

## Frontend (Next.js)

Responsible for:

- Problem metadata

- Submission trigger
- User state
- Database interaction
- Rendering execution results
- Displaying queue state

---

## Execution Service

Input:

```json
{
  "questionId": "string",
  "language": "string",
  "sourceCode": "string",
  "mode": "run" | "submit"
}
```

Responsibilities:

* Load canonical test cases (file-based)
* Compile code (if required)
* Execute per test case
* Enforce time limits
* Compare outputs deterministically
* Enforce execution queue
* Enforce source size limits
* Enforce test input size limits
* Return deterministic result object
* Clean up execution environment

Does NOT:

* Access MongoDB
* Know user identity
* Store problem description
* Store submissions
* Persist state

# 5. Execution Model

## Process-Based Sandbox

For each submission:

1. Acquire execution slot (see Concurrency Policy).
2. Create unique temporary directory.
3. Set process `cwd` to temporary directory.
4. Write source file inside temporary directory.
5. Compile (if required).
6. For each test case:
   * Feed input via stdin.
   * Measure execution time.
   * Capture stdout/stderr.
   * Normalize output.
   * Compare against expected output.
7. Aggregate results.
8. Delete temporary directory.
9. Release execution slot.

No containers.

No VM isolation.

No kernel namespace isolation.

---

# 6. Concurrency Policy

V1 enforces:

Behavior:

* If execution is idle → start immediately.
* If execution running → enqueue request.
* If queue full → reject request (HTTP 429).

Purpose:

* Prevent CPU overload.
* Prevent memory exhaustion.
* Prevent fork amplification.
* Maintain predictable latency.

Frontend must display:

* “Queued” state when submission is waiting.

# 9. Output Normalization Policy

Before comparison:

* Convert `\r\n` → `\n`
* Trim trailing whitespace per line

Strict rules:

* Missing lines → WRONG_ANSWER
* Extra lines → WRONG_ANSWER
* Floating point tolerance → NOT supported
* Case-insensitive comparison → NOT supported

Exact match required after normalization.

---

# 10. Source & Input Guardrails

To prevent abuse:

* Maximum source code size: 100 KB
* Maximum input size per test case: bounded (defined per problem)

Requests exceeding limits are rejected.

---

# 11. Secure Process Execution Rules

Compilation and execution must:

* Use direct argument arrays.
* Never use shell string concatenation.
* Never use `exec("g++ " + userInput)`.

Explicitly:

* No shell interpolation.
* No user-controlled command injection.
* All commands invoked via argument arrays.

---

# 12. Error Classification Model

Normalized states:

* SUCCESS
* COMPILATION_ERROR
* RUNTIME_ERROR
* TIME_LIMIT_EXCEEDED
* WRONG_ANSWER
* OUTPUT_MISMATCH
* SANDBOX_FAILURE
* SYSTEM_CRASH

Deterministic mapping rules apply.

---

# 13. Isolation Guarantees (Actual)

V1 guarantees:

* No database access
* No service-layer access
* No user identity access
* No environment secrets passed
* Unique temp directory per execution
* `cwd` restricted to temp directory
* Clean environment variables
* No hidden test leakage
* Deterministic output comparison

V1 does NOT guarantee:

* Kernel-level network isolation
* System call filtering
* Process count limits
* Strict memory cgroups
* Namespace-level file isolation

---

# 14. Determinism Guarantees

Ensured by:

* File-based canonical tests
* Fixed compiler/runtime versions
* Strict normalization rules
* No AI judging
* Single execution concurrency

Same input → same output → same result.

---

# 15. Upgrade Path (V2 Direction)

V2 must introduce:

* Container-based sandboxing
* Memory cgroups
* CPU quotas
* Process count limits
* Network namespace isolation
* Execution worker pool

Execution interface remains unchanged.
