# V1 Requirements — CodeSphere

## Status: Frozen (Aligned with Execution Engine V1)

This document defines functional and non-functional requirements
for Version 1.

V1 targets controlled demo scale, not adversarial multi-tenant usage.

---

# 1. Functional Requirements

## 1.1 Authentication

- Email/password registration
- Secure password hashing
- Session-based login
- Protected routes
- Logout functionality
- Session validation on protected endpoints

---

## 1.2 Problem Listing

- Display all canonical problems
- Show metadata:
  - Title
  - Difficulty
  - Tags
  - User progress status
- No hidden test data exposed

---

## 1.3 Problem Detail View

- Display full problem statement
- Display visible examples
- Display user submission history for that problem
- Provide editor for code submission

---

## 1.4 Submission System

- Accept source code (max 100KB)
- Validate language selection
- Validate authentication
- Enforce authorization
- Enforce submission queue constraints
- Evaluate against deterministic test cases
- Enforce:
  - Per-test timeout (2s)
  - Global timeout (2 × test count)
- Enforce input size bounds
- Normalize output strictly
- Classify results:
  - Accepted
  - Wrong Answer
  - Runtime Error
  - Time Limit Exceeded
  - Compilation Error

If execution slot is occupied:

- Submission enters queued state

If queue full:

- Submission rejected

---

## 1.5 Submission Persistence

For each submission:

- User ID
- Problem ID
- Source code
- Timestamp
- Execution result status
- Per-test result metadata
- Total runtime
- Average runtime

Persistence must occur only after execution completes.

---

## 1.6 Progress Tracking

For each user-problem pair:

- Status:
  - Not Attempted
  - Attempted
  - Solved
- Last attempt timestamp
- Total submissions count

Rules:

- First submission → Attempted
- First SUCCESS → Solved
- Solved state remains unless future version changes logic

---

## 1.7 Basic Dashboard

- Total solved
- Total attempted
- Recent submissions
- Simple progress summary

No advanced analytics.

---

# 2. Non-Functional Requirements

## 2.1 Security

- Strong password hashing
- Session protection
- Input validation
- No hidden test case leakage
- No direct DB exposure
- No shell interpolation in execution
- Argument-array-only process invocation
- Clean execution environment
- No secret propagation to execution layer

---

## 2.2 Reliability

- No state corruption
- Deterministic evaluation
- Atomic submission + progress update
- Queue-bounded execution
- Controlled concurrency (1 at a time)
- Safe rejection when queue full

---

## 2.3 Maintainability

- Strict layer separation
- Canonical content isolated
- No domain logic in controllers
- Execution engine swappable
- Repositories persistence-only
- Services framework-agnostic

---

## 2.4 Performance

- Efficient problem loading
- Indexed MongoDB queries
- Bounded evaluation time
- Predictable latency under small-scale load
- Queue prevents CPU overload

---

## 2.5 Testability

- Authorization testable independently
- Execution engine testable in isolation
- Services testable without HTTP
- Problem loader testable without DB
- Queue behavior testable deterministically

---

# 3. Scale Assumptions

V1 is designed for:

- 30–300 total users
- Limited simultaneous submissions
- Controlled demo usage

It is not designed for:

- Public adversarial multi-tenant judge
- Horizontal scaling
- Enterprise-grade isolation

---

# 4. Completion Criteria

V1 is complete when:

- User can register and login.
- User can view problems.
- User can submit solutions.
- Execution engine enforces queue policy.
- Execution enforces strict time limits.
- Results are deterministic.
- Submissions are persisted correctly.
- Progress updates are atomic.
- Hidden tests are never exposed.
- Architecture constraints are respected.
