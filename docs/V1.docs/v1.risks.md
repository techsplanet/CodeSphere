# CodeSphere V1 — Risk Assessment

This document defines the explicit security and operational risks of V1.

This is an honest assessment aligned with actual guarantees.

---

# 1. Risk Categories

## A. Malicious Code

Examples:

- File system probing
- Socket calls
- Environment inspection

Mitigated by:

- No secrets passed
- No DB access
- Temp directory isolation
- Clean environment variables

Not prevented:

- Raw socket attempts
- System file reads if OS permits

Status:

Application-level mitigation only.
Not OS-hardened.

Acceptable for controlled demo scale.
Not safe for adversarial multi-tenant judge.

---

## B. Fork Bombs

Example:

while(true) fork();

Mitigated by:

- 2-second per-test timeout
- Global timeout
- Concurrency limit = 1
- Bounded execution window

Not prevented:

- Rapid short-lived process spawning inside timeout window
- No ulimit enforcement

Status:

Partially mitigated.
Impact window strictly time-bounded.

Acceptable for V1.

---

## C. Memory Exhaustion

Java:

- Heap capped at 128MB

C++ / Python:

- No strict memory cap
- OS may terminate process on OOM

Mitigated by:

- Concurrency limit = 1
- VM-level memory ceiling
- Short execution windows

Not prevented:

- Temporary high memory allocation
- Possible OOM crash under abuse

Status:

Moderately mitigated.
Not container-isolated.

---

## D. CPU Exhaustion

Infinite loops:

Mitigated by:

- Per-test timeout
- Global timeout
- Single concurrency

Status:

Strongly mitigated.

---

## E. Spam Submissions

Mitigated by:

- Concurrency limit
- Queue size limit
- Optional API rate limiting

Status:

Operationally controlled.

---

# 2. Security Classification

V1 is safe for:

- Controlled demo
- Limited user base (30–300)
- Low adversarial risk

V1 is NOT safe for:

- Public open competitive judge
- Multi-tenant hostile environment
- High-scale execution workloads

---

# 3. Operational Risk Summary

| Risk Category     | V1 Status            |
| ----------------- | -------------------- |
| Malicious Code    | App-level mitigated  |
| Fork Bomb         | Time-bounded         |
| Memory Exhaustion | Moderately mitigated |
| CPU Exhaustion    | Strongly mitigated   |
| Spam              | Queue-controlled     |

---

# 4. Upgrade Requirements (V2)

To eliminate remaining risks:

- Container-based execution
- cgroups memory limits
- CPU quotas
- Process count limits
- Network namespace isolation
- Worker-based architecture

---

# Final Statement

V1 execution engine is intentionally:

- Deterministic
- Queue-controlled
- Risk-aware
- Honest about isolation limits

It is not enterprise-hardened.
It is architecturally clean and upgrade-ready.
