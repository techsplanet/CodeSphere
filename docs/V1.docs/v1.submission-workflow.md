# V1 Submission Workflow — CodeSphere

## Status: Frozen (Aligned with Execution Engine V1)

This document defines the complete lifecycle of a submission in V1,
including validation, queue behavior, execution, persistence,
progress updates, and failure handling.

This workflow assumes:

- Process-based deterministic execution
- Single concurrency execution engine
- Max queue length = 3
- Atomic persistence guarantees

---

# 2. Submission Entry Point

## 2.1 Frontend Submission

User submits:

- problemId
- language
- sourceCode

Frontend must:

- Validate non-empty source
- Enforce client-side size hint (optional)
- Handle "Queued" state response

---

## 2.2 API Layer

API:

- Validates session
- Extracts authenticated identity
- Delegates entirely to Service Layer
- Does not execute code
- Does not access database directly

---

# 3. Service Layer Workflow

The Service Layer is responsible for orchestration.

## Step 1 — Authentication Validation

- Ensure user session valid
- Resolve domain identity
- If invalid → return 401

---

## Step 2 — Authorization Enforcement

- Verify user allowed to submit
- If unauthorized → return 403

Authorization must occur before any execution.

---

## Step 3 — Input Guardrails

Validate:

- Source code size ≤ 100KB
- Language supported
- Problem exists
- Execution mode valid

If invalid → return 400

No execution triggered if validation fails.

---

## Step 4 — Execution Request

Service sends request to Execution Engine:

```json
{
  "questionId": "...",
  "language": "...",
  "sourceCode": "...",
  "mode": "submit"
}
```

---

# 4. Execution Engine Behavior

## 4.1 Queue Model

Execution engine enforces:

If execution idle:

* Start immediately.

If busy and queue not full:

* Enqueue request.
* Return status: QUEUED.

If queue full:

* Reject request.
* Service returns HTTP 429.

---

## 4.2 Execution Phase

When execution begins:

* Temp directory created
* Source written
* Compile (if needed)
* Per-test execution
* Timeout enforcement
* Output normalization
* Deterministic comparison
* Temp directory cleaned

Execution returns:

No DB interaction occurs here.

---

# 5. Post-Execution Persistence

Once execution completes successfully (even if result is failure like WRONG_ANSWER):

Service performs atomic update:

## 5.1 Create Submission Record

Persist:

* userId
* problemId
* sourceCode
* status
* totalRuntime
* averageRuntime
* testCaseResults
* timestamp

---

## 5.2 Update Progress Record

For user-problem pair:

If first submission:

* Create record
* Status = Attempted

If SUCCESS:

* Status = Solved

Increment submission count.

Update lastAttempt timestamp.

---

## 5.3 Atomicity Requirement

Submission creation + progress update must be atomic.

Allowed strategies:

* MongoDB transaction

  OR
* Idempotent write logic ensuring consistency

No partial state allowed:

* No submission without progress update.
* No progress update without submission record.

---

# 6. Response to Client

Service returns:

* overallStatus
* testCaseResults (IDs only)
* totalRuntime
* averageRuntime
* queue status if applicable

Hidden test data is never returned.

Frontend must:

* Display result clearly
* Update progress indicators

---

# 7. Failure Scenarios

## 7.1 Authentication Failure

→ 401

No execution triggered.

---

## 7.2 Authorization Failure

→ 403

No execution triggered.

---

## 7.3 Validation Failure

Examples:

* Source too large
* Unsupported language
* Problem not found

→ 400

No execution triggered.

---

## 7.4 Queue Full

→ 429

Execution not enqueued.

---

## 7.5 Execution Failure Types

Execution may return:

* COMPILATION_ERROR
* RUNTIME_ERROR
* TIME_LIMIT_EXCEEDED
* WRONG_ANSWER
* SYSTEM_CRASH
* SANDBOX_FAILURE

All are persisted as valid submission outcomes.

---

## 7.6 Engine Crash

If execution service crashes:

* Return SYSTEM_CRASH
* Do not partially persist state
* No inconsistent progress updates

---

# 8. Determinism Guarantee

Submission result must depend only on:

* Source code
* Language
* Canonical test cases

Not dependent on:

* Request timing
* Queue order
* Environment randomness
* User identity

Same input → same result.

---

# 9. Concurrency Behavior Summary

At most:

* 1 execution running
* 3 submissions queued

Effects:

* Predictable resource usage
* Stable CPU usage
* Bounded memory pressure

---

# 10. Explicit Non-Goals (V1 Discipline)

Not included:

* Background job workers
* Distributed queue
* Parallel execution
* Partial scoring
* Contest ranking
* Real-time streaming judge
* Horizontal scaling

All execution is synchronous and local.

---

# 11. Upgrade Path (V2)

Future changes:

* Execution moves to container-based worker
* Queue becomes distributed
* Worker updates submission status asynchronously
* API becomes polling-based

Service contract remains unchanged.

---

# Final Statement

V1 submission workflow guarantees:

* Deterministic evaluation
* Strict authorization
* Queue-controlled execution
* Atomic persistence
* No hidden test leakage
* Layer integrity maintained

This workflow is:

* Stable at small scale
* Honest about limits
* Architecturally clean
* Upgrade-ready
